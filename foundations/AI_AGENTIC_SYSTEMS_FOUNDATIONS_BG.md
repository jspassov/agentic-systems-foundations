# AI Agentic Systems Foundations — концептуална рамка

## Статус

Този документ е conceptual baseline (концептуална отправна точка) за бъдещ курс по AI agents (агенти с изкуствен интелект) и agentic systems (агентни системи).

Работни формулировки като **human-in-the-loop scaffolded LLM workflow (работен процес с езиков модел, с човек в цикъла и външна управляваща рамка)** и **deterministic shell, bounded agentic core (детерминистична обвивка и ограничено агентно ядро)** са инженерни описания, а не твърдение за нормативен стандарт.

## 1. Основен мисловен модел

Agentic systems (агентните системи) не трябва да се учат като списък от продукти. Полезно е системата да се разглежда на слоеве:

```text
APPLICATION
    │
WORKFLOW
    │
AGENT
    │
RUNTIME / ORCHESTRATOR
    │
    ├── TOOLS
    ├── MEMORY / STATE
    └── MODELS
         │
     MCP / APIs / SDKs
         │
   EXTERNAL WORLD
```

## 2. Какво е AI agent (агент с изкуствен интелект)

> **AI agent (агент с изкуствен интелект) е софтуерна система, която получава цел, възприема текущото състояние на средата, самостоятелно избира следващи действия и използва разрешени tools (инструменти), за да постигне целта, като оценява резултатите от действията си и при нужда променя поведението си.**

```text
Goal (цел)
   ↓
Observe (наблюдавай)
   ↓
Decide (реши)
   ↓
Act (действай)
   ↓
Observe result (наблюдавай резултата)
   ↓
Decide again (реши отново)
   ↓
...
   ↓
Goal reached / Stop
```

Ключовата характеристика е bounded autonomy (ограничена автономност).

## 3. LLM (голям езиков модел) не е автоматично agent (агент)

```text
Prompt → LLM → Answer
```

е използване на LLM, но не непременно агент.

```text
A → B → C → D
```

е workflow (работен процес), но също не непременно агент.

Агентно поведение възниква, когато системата може динамично да избира следваща стъпка според целта, състоянието и резултатите от предишните действия.

## 4. Workflow (работен процес) срещу Agent (агент)

Workflow:

```text
A
↓
B
↓
C
↓
D
```

Agent:

```text
A
↓
LLM решава
↓
може B
може C
може D
може пак A
```

> **Workflow = developer-defined control flow (предварително определена логика на изпълнение).**

> **Agent = model-influenced control flow (логика на изпълнение, върху която моделът влияе).**

## 5. Tool (инструмент)

Tool (инструмент) е конкретна capability (възможност) за действие: търсене, четене на e-mail, заявка към база данни, запис във файл, извикване на API (програмен интерфейс) и др.

> **Agent (агентът) решава какво да направи. Tool (инструментът) извършва конкретното действие.**

## 6. Skill (умение)

Skill (умение) няма напълно универсално значение между платформите.

За целите на курса:

> **Skill (умение) е пакет от инструкции, процедура и евентуално tools (инструменти), който описва как се изпълнява определен тип задача.**

## 7. MCP

MCP (Model Context Protocol — протокол за контекст на модела) не е agent и не е tool.

Той е protocol (протокол), чрез който tools (инструменти), resources (ресурси) и други capabilities (възможности) могат да бъдат предоставени по стандартизиран начин.

> **Tool е възможност. MCP е стандартизиран начин тази възможност да бъде предоставена.**

## 8. Runtime / Orchestrator

Runtime (средата за изпълнение) или orchestrator (оркестраторът) управлява жизнения цикъл на агентния процес: state (състояние), checkpoints (контролни точки), retries (повторни опити), routing (маршрутизиране), pause/resume (спиране/продължаване), timeouts (времеви ограничения) и execution traces (следи от изпълнението).

## 9. n8n и LangGraph

Работен модел:

- **n8n** — workflow-centric orchestrator (оркестратор, ориентиран към работния процес);
- **LangGraph** — agent/state-centric runtime (среда за изпълнение, ориентирана към агента и състоянието).

Те не трябва да се преподават като взаимно изключващи се технологии.

## 10. Локален или cloud LLM (облачен голям езиков модел)

LLM може да бъде cloud (облачен), local (локален) или hybrid (хибриден). Това не променя самото понятие за агент.

## 11. Human-in-the-loop scaffolded LLM workflow

Нашият изходен практически модел е:

> **Human-in-the-loop scaffolded LLM workflow (работен процес с езиков модел, с човек в цикъла и външна управляваща рамка).**

```text
.md файлове в repository (хранилище)
        ↓
правила / процедури / контекст / решения
        ↓
Human (човекът)
        ↓
ChatGPT / LLM
        ↓
reasoning (разсъждение)
        ↓
конкретна задача
        ↓
резултат
        ↓
човекът решава какво следва
```

В този модел човекът е основният orchestrator (координатор на изпълнението).

Markdown файловете могат едновременно да играят ролята на policy (правила), procedure (процедура), workflow definition (описание на работен процес), context (контекст), state snapshot (моментна снимка на състоянието), knowledge (знание) и prompt template (шаблон за инструкция).

## 12. От „юзди“ към agent

```text
Prompt
 ↓
Prompt + правила
 ↓
Prompt + правила + repository
 ↓
Workflow definition
 ↓
Skill
 ↓
Agent
 ↓
Agent Runtime
```

Ключовият преход е част от решението „какво следва“ да бъде делегирано на системата.

## 13. Deterministic shell, bounded agentic core

> **Deterministic shell, bounded agentic core (детерминистична обвивка и ограничено агентно ядро).**

```text
Human
    ↓
Goal + Policies
    ↓
Deterministic code
    ├─ права
    ├─ разрешени инструменти
    ├─ допустими данни
    ├─ лимити
    ├─ валидиране
    └─ човешко одобрение
              ↓
Agent
              ↓
"Как да постигна целта?"
              ↓
избира допустимо действие
              ↓
Deterministic check
              ↓
Tool
```

Автономността не означава липса на контрол. Човекът преминава от „Аз решавам всяка следваща стъпка“ към „Аз определям целта, разрешеното пространство за действие и точките, в които агентът трябва да се върне при мен“.

## 14. Guardrails (защитни ограничения)

Guardrails се проектират заедно с autonomy (автономността), а не след това.

Меко ограничение:

```text
"Не изпращай e-mail без мое разрешение."
```

Твърдо ограничение:

```text
if action == SEND_EMAIL:
    require_human_approval()
```

Работна класификация:

```text
Правило
  │
  ├─ поведенческо → instruction (инструкция)
  ├─ процесно → workflow logic (логика на работния процес)
  └─ security-critical → code / policy engine
```

Критичните security controls (контроли за сигурност) трябва да бъдат налагани независимо от LLM.

## 15. GUI / no-code / low-code

GUI (графичният интерфейс), drag-and-drop (влаченето и пускането), no-code (без код) и low-code (разработка с малко код) могат да намалят техническата бариера, но не премахват архитектурната отговорност.

> **Инструментът може да скрие сложността, но не премахва сложността.**

Способността да произведеш код или workflow не е равна на способността да проектираш безопасна система.

## 16. Методологичен принцип за обучение

Препоръчителният learning workflow (учебен процес) е:

```text
1. Software thinking
   (софтуерно мислене)

2. Deterministic workflow
   (детерминистичен работен процес)

3. Tools + APIs + Identity
   (инструменти + програмни интерфейси + идентичност)

4. LLM integration
   (интегриране на голям езиков модел)

5. Agent loop
   (цикъл на агента)

6. Guardrails + Trust Boundaries
   (защитни ограничения + граници на доверие)

7. Testing + Observability
   (тестване + наблюдаемост)

8. Frameworks / n8n / LangGraph
   (рамки и платформи)
```

> **Framework / GUI е implementation choice (избор за реализация), а не заместител на разбирането.**

## 17. Предварителна структура на курс

Работна посока: 8 модула × 4 академични часа = 32 академични часа.

1. От LLM до AI agent

3. Tools, APIs, identity и MCP
4. LLM в deterministic workflow
5. Първият истински agent
6. Security и guardrails
7. Testing, evals и observability
8. Frameworks и реализация

Това не е финализирана учебна програма. Подробното разработване е отделен етап.
